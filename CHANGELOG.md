# Changelog

## [Unreleased]

### Fixed
- **Crossroads item value preserved end-to-end** (`donate_item`/`claim_item` in `backend/multiplayer/crossroads.py`): donating an item to the Crossroads previously discarded its `value`, so `claim_item()` always created the claimed Discovery with a hardcoded `value=0`, making Crossroads transfers economically pointless (every claimed item became a value-0 artifact). `donate_item()` now captures the donated discovery's `value` (from the first matched discovery) and stores it on the `CrossroadsItem`, and `claim_item()` now creates the claimed Discovery with `value=item_data.get('value', 0)`. A new `value INTEGER NOT NULL DEFAULT 0` column was added to the `crossroads_items` table in `backend/multiplayer/database.py` (exposed through `save_crossroads_item`, `get_available_items`, `claim_item`, and `claim_item_partial`), with an idempotent `_ensure_value_column()` migration that `ALTER TABLE`s in the column only when it's missing (for DBs created before the change). `CrossroadsItem` gained a `value: int = 0` field with `to_dict`/`from_dict` support (`from_dict` defaults to 0). Covered by new regression tests in `tests/test_multiplayer.py` (value roundtrip, `from_dict` default, and migration adds column).
- **Crossroads listing endpoints now verify the game exists** (`api_crossroads_items`, `api_crossroads_lore`, and `api_crossroads_messages` in `backend/multiplayer/api.py`): the three Crossroads read/listing endpoints (`GET /api/crossroads/items`, `GET /api/crossroads/lore`, and `GET /api/crossroads/messages`) previously called `_authorize_game()` but never confirmed that the supplied `game_id` resolved to an actual game, so an unknown/nonexistent `game_id` still returned the shared Crossroads listings. Each endpoint now calls a `_game_exists(game_id)` check immediately after `_authorize_game()` (still inside the per-game `with _locked(game_id):` block) and raises HTTP 404 with detail `"Game not found"` when the game cannot be resolved. Authorization is unchanged and still runs first (missing/invalid token under enforcement returns 403), and the new 404 applies whether or not token enforcement is enabled. Covered by the updated and new regression tests in `tests/test_multiplayer.py` (the read-path tests now create a real game via a `_ensure_game()` helper, plus tests asserting 404 for `nonexistent-game-xyz`/`unknown-game-xyz`, 404 with enforcement disabled, and 200 for a live game).
- **Spectator game listing no longer races the in-memory store** (`api_spectate_games` in `backend/api/spectate.py`): the endpoint previously iterated `list(GAME_STORE.items())` and membership-tested `row["id"] in GAME_STORE` directly, so a concurrent `evict_if_needed` (which pops from the LRU `OrderedDict` under `_store_lock`) or `register_game` could mutate the store mid-iteration and raise `RuntimeError: dictionary changed size during iteration` (HTTP 500), and the separate membership test and per-game lookup were a check-then-act race. A new `snapshot_games()` helper in `backend/game/manager.py` takes `_store_lock` and returns a stable `list(GAME_STORE.items())` snapshot in current LRU order without mutating the store (no `touch_game`, no reordering); `api_spectate_games` now derives both the `active` flag and the never-persisted in-memory games section from that single locked snapshot. Covered by tests in `tests/test_api.py`.
- **Corrupt `faction_relations` in a save no longer raises a `KeyError`→HTTP 500** (`_state_from_dict` in `backend/game/manager.py`): a saved game whose `faction_relations` held a non-dict entry raised `AttributeError` on `.items()` and one missing the `faction_id` key raised `KeyError`, both of which surfaced as an unhandled exception (HTTP 500) instead of the documented clean-404 behavior. `faction_relations` reconstruction now skips any non-dict entry with a `Skipping malformed faction_relation` warning and falls back to the dict key for `faction_id` (`fr_data.get("faction_id", fid)`), while `reputation`/`known` already default safely. As a final safety net, the whole reconstruction body of `_state_from_dict` is wrapped in a `try`/`except (KeyError, TypeError, ValueError, AttributeError)` that logs `Corrupt save for %r: failed to reconstruct state` and returns `None`, so any unforeseen failure while rebuilding a nested field (e.g. a malformed `systems` or `events` section) yields a clean 404 rather than a 500. Covered by the new `TestStateFromDictCorruptSections` class in `tests/test_generation.py` (missing `faction_id` fallback, non-dict entries skipped, malformed `systems`/`events` returning `None`).
- `snapshot_games()` added to `backend/game/manager.py`: returns a lock-safe point-in-time snapshot of the in-memory `GAME_STORE` (a `list` of `(game_id, GameState)` tuples in LRU order) taken under `_store_lock`, so callers that iterate the store do not race concurrent eviction/registration; it does not refresh LRU recency.

### Security
- **Per-game lock TOCTOU race closed via lease/refcount tracking**: Fixed a get-then-acquire TOCTOU race in the per-game lock registry in `backend/api/routes.py`, where a lock could be evicted between being fetched and acquired, allowing two threads to mutate the same game concurrently. A new `_locked(game_id)` context manager increments a per-game refcount (`_lock_refcounts: dict[str, int]`) while holding `_lock_for_locks`, then acquires the game lock, and decrements/cleans up in a `finally` block. The lock registry sweep/eviction paths (the periodic sweep, the hard-cap eviction, `_cleanup_game_lock`, and `_cleanup_stale_locks`) now skip entries with an outstanding lease (refcount > 0). All game-scoped endpoints in `backend/api/routes.py` and `backend/multiplayer/api.py` now use `with _locked(game_id):` instead of `with _get_lock(game_id):`. `_get_lock()` remains as the raw fetch-or-create primitive, `_fetch_or_create_unlocked(game_id)` is the extracted shared helper (caller must hold `_lock_for_locks`), and `_locked_game_ids()` now also reports leased locks. Covered by tests in `tests/test_api.py`.
- **Type annotations + mypy fixes (no behavioral change)**: Added type annotations (e.g. `Generator` import and generator return type on `_locked`) and fixed mypy errors across `backend/api/routes.py` and `backend/multiplayer/api.py`. No behavior change. Later, `backend/database.py` gained a `typing.Any` import and explicit `value: Any` parameter annotations on the defensive `_safe_list_len` and `_safe_int` helpers. No behavior change.
- **Bounded per-game lock registry + fail-fast unknown-game rejection**: `_get_lock()` in `backend/api/routes.py` no longer uses an unbounded `itertools.count` access counter and now enforces a hard cap `_MAX_TRACKED_LOCKS = 1024`. A periodic sweep runs at most every `_SWEEP_INTERVAL_SECONDS = 5.0` (or immediately when the registry exceeds the cap), evicting least-recently-accessed entries that are not currently held, preferring entries whose game_id is not in `GAME_STORE`. This prevents unbounded memory growth (a DoS vector) from requests using many non-existent game_ids. Additionally, all game-scoped endpoints now call `_ensure_game_exists(game_id)` (backed by `_game_id_is_known()`, which checks `GAME_STORE` and then the `games` table via `game_exists`, failing closed on DB errors) and return HTTP 404 `"Game not found"` before acquiring a lock or running authorization for a game_id that cannot be resolved to a known game. Note the subtle behavior change: unknown game_ids now return 404 rather than 403/other responses. Covered by tests in `tests/test_api.py` and `tests/test_multiplayer.py`.
- **`GET /api/leaderboard` disabled while token enforcement is on** (`api_leaderboard` in `backend/api/routes.py`): the leaderboard endpoint now returns HTTP 403 with detail `"Leaderboard disabled while game token enforcement is enabled"` whenever per-game token enforcement is enabled (via `get_require_game_token()`), which is the secure default. The rationale: the endpoint exposes player-chosen ship names and in-game credits (cross-tenant, identity-adjacent data) and cannot be authoritatively scoped to a single caller, so it is disabled while enforcement is on, mirroring the guard already used by the spectator game listing (`GET /api/spectate/games`). Operators running a purely local, single-user deployment can opt back in via `STARFARER_ALLOW_NO_AUTH=1`. Covered by `TestLeaderboardEnforcement` in `tests/test_access_control.py`.
- **`AcceptMissionRequest.faction_id` validation**: The `faction_id` field on `AcceptMissionRequest` (`backend/api/schemas.py`) is now validated via a `@field_validator`, so arbitrary, unknown, or whitespace-only faction ids are rejected at validation time with HTTP 422 instead of being trusted.
- **Default-on per-game token enforcement (IDOR fix)**: Per-game token access control is now **ON by default** (secure baseline), so multi-user deployments are no longer vulnerable to IDOR on game-scoped endpoints. Previously `get_require_game_token()` returned `False` by default, which allowed any caller to act on a victim's game (e.g. `POST /api/crossroads/donate-item` with `{"game_id": "<victim>"}`) when `STARFARER_REQUIRE_GAME_TOKEN` was unset. New precedence in `backend/config.py::get_require_game_token()`: (1) a truthy `STARFARER_ALLOW_NO_AUTH` disables enforcement (the ONLY safe way to run without auth, for purely local single-user play — never set it in a shared/networked deployment); (2) otherwise an explicitly-set `STARFARER_REQUIRE_GAME_TOKEN` is honored (truthy = on, falsy = off, preserving backwards compatibility); (3) otherwise enforcement defaults to ON. Adds `get_allow_no_auth()` in `backend/config.py`, updates the `_authorize_game()` docstring in `backend/api/routes.py`, and adds a `TestIdorRegression` regression test asserting that `POST /api/crossroads/donate-item` without a valid `X-Game-Token` is rejected with HTTP 403 while the correct token succeeds.
- **Per-IP rate limiting on `POST /api/game/new`** (`_check_new_game_rate_limit` in `backend/api/routes.py`): the new-game endpoint now enforces a per-IP sliding-window rate limit to defend against unauthenticated DoS. Configurable via `STARFARER_NEW_GAME_RATE_LIMIT` (max requests per IP per window; default `30`; a value `<= 0` disables the limit entirely, read via `get_new_game_rate_limit()` in `backend/config.py`) and `STARFARER_NEW_GAME_RATE_WINDOW` (window duration in seconds; default `60.0`, read via `get_new_game_rate_window()`). Exceeding the limit returns HTTP 429 with detail `"Too many new-game requests. Please wait and retry."` and a `Retry-After` response header (seconds). The per-IP table is bounded to `_MAX_RATE_LIMIT_IPS = 4096` entries, evicting the oldest entry when the cap would be exceeded. A `reset_new_game_rate_limiter()` helper (used by tests) clears the table.
- **Reverse-proxy caveat documented for `_client_ip` / the new-game rate limiter**: `_client_ip()` in `backend/api/routes.py` keys the per-IP rate limit on the direct peer address (`request.client.host`) and ignores `X-Forwarded-For`/`Forwarded`; behind a reverse proxy every client therefore shares one rate-limit bucket and can collectively exhaust `STARFARER_NEW_GAME_RATE_LIMIT`. Operators behind a proxy must configure trusted client-IP handling (e.g. uvicorn `--forwarded-allow-ips`); documented in `backend/api/routes.py`, `README.md`, and `HOWTOPLAY.md`.
- **Stored-game upper bound on `POST /api/game/new`** (`_enforce_stored_game_cap` in `backend/api/routes.py`): before saving a new game, the endpoint enforces an upper bound on the number of stored games. Configurable via `STARFARER_MAX_STORED_GAMES` (caps the number of rows in the `games` table; default `100000`; a value `<= 0` disables the cap, read via `get_max_stored_games()` in `backend/config.py`). A new `count_games()` helper in `backend/database.py` returns the current stored-game count; when that count meets or exceeds the cap, the endpoint raises HTTP 429 with detail `"New-game limit reached. Please try again later."`.

### Fixed
- **`POST /api/game/new` default `shared_universe`**: Omitting `shared_universe` from a new-game request now defaults to `True` (the canonical shared universe), fixing a contradiction where an omitted value was silently coerced to `False`. Previously `api_new_game` in `backend/api/routes.py` passed `False` when `shared_universe` was `None`; now `NewGameRequest.shared_universe` in `backend/api/schemas.py` has a non-None default of `True` and is passed straight through. This aligns the API default with `GameState.shared_universe = True` and `new_game(..., shared_universe=True)`. Covered by a regression test in `tests/test_api.py`.

Covered by new tests in `tests/test_api.py::TestAPILeaderboardMalformedState` (malformed `discoveries` as null/dict/string, `systems_visited` as string/bool, valid-state extraction, and direct helper tests).
- **Spectator web UI no longer reads the game token from the `token` URL query parameter** (`getToken` in `webui/js/api.js` and `boot` in `webui/js/main.js`): previously `getToken()` resolved the long-lived per-game token from the `token` URL search param first, then from `localStorage['starfarer_game_token']`, and `boot()` called `setToken(params.get('token'))` whenever a `?token=` was present in the address bar — so the long-lived game token could be passed via a URL, defeating the stream-ticket leak protection and leaking the token into browser history, logs, and `Referer` headers. `getToken()` now resolves the token **only** from `window.localStorage` under the `starfarer_game_token` key (never from the URL), and `main.js` gained an exported `stripUrlToken()` helper that removes a stray `token` query parameter from the address bar on load via `window.history.replaceState` (called at the start of `boot()`), while the old `setToken(params.get('token'))` call was removed. Covered by `tests/test_webui_url_token_leak.py`, which asserts `getToken()` does not read from the URL and still reads localStorage, and that `main.js` strips the URL token.
- **Distress beacons and salvage now produce varied outcomes across repeated attempts** (`activate_distress_beacon` and `perform_salvage` in `backend/game/engine.py`): both actions previously seeded their RNG with only the game seed, system/body id, and (for salvage) the attempt count, so repeating the action under the same conditions replayed an identical outcome — a distress beacon in a given system always gave the same rescue result, and salvage on a given body repeated the same roll. Both now include `str(state._next_log_id)` in the `seeded_random(...)` call, so each successive activation/attempt derives a fresh, deterministic sub-seed and produces varied outcomes while keeping the universe itself reproducible. Covered by tests in `tests/test_game_engine.py`.
- **Cargo sorting on `GET /api/game/{id}` now triggers when either `sort` or `order` is supplied** (`_full_state_response` in `backend/api/routes.py`): previously cargo items in the full game state response were sorted only when **both** the `sort` and `order` query parameters were supplied, so sending just one (e.g. `?sort=value`) silently returned unsorted cargo. Now providing **either** `sort` or `order` triggers sorting, with the missing parameter defaulting (`sort` -> `value`, `order` -> `desc`), and an invalid `sort` (not `value`/`name`) or `order` (not `asc`/`desc`) value returns HTTP 422 even when only one is supplied. - **Discovery IDs are now unique and independent of RNG state** (`_generate_discovery` and `perform_salvage` in `backend/game/engine.py`): discovery IDs were previously derived from the seeded RNG (`f"{rng.getrandbits(48):012x}"`), so two discoveries generated with the same RNG state could receive an identical 12-hex-character ID. This could surface when the RNG seed (which incorporates the discovery count / inventory size) repeated — for example, re-exploring a body at the same `len(state.discoveries)` — producing colliding discovery IDs across sells or spare-parts salvages. Discovery IDs are now generated with `uuid.uuid4().hex[:12]`, which is independent of the deterministic RNG state and guarantees distinct IDs per discovery while preserving the 12-character hex format. Note this is intentionally **not** part of the deterministic, seed-based universe generation: discovery instance IDs are opaque identifiers, not reproducible content. Covered by `TestDiscoveryIdUniqueness` (`test_explore_surface_ids_unique_across_sells`) and `test_perform_salvage_spare_parts_ids_unique` in `tests/test_game_engine.py`.

It now uses peek-then-pop under the lock: a ticket bound to a different `game_id` is rejected and **not** consumed (left in the store), so it remains redeemable for the game it was minted for, while a matching ticket is always popped (single-use) even when expired; the function returns `True` only when the ticket existed, matched `game_id`, and had not yet expired. `api_spectate_stream` in `backend/api/spectate.py` now reads token enforcement once up front and applies an explicit authorization order: (1) a valid single-use ticket authorizes and is consumed, even if a stray/bogus `X-Game-Token` header is present; (2) otherwise the `X-Game-Token` header is checked; (3) otherwise, when enforcement is on, the request fails closed (HTTP 403, or 404 when the game cannot be resolved); when enforcement is disabled and no credential is supplied, the request is allowed. Items and lore endpoints also gained pagination (`page`/`per_page`, default 25, max 50).
- `perform_bulk_sell` (backend/game/trading.py) no longer silently clamps to available stock when an entry's requested `quantity` exceeds the number of matching discoveries. Such an over-quantity entry is now rejected entirely (none of its units are sold) with an error reported, while valid sibling entries in the same request still sell (partial failure preserved). Previously the request sold all available matching units of that entry.
- Crossroads `donate_item` (`POST /api/crossroads/donate-item`) now rejects non-positive or non-integer `quantity` values before any cargo mutation: a service-layer guard in `backend/multiplayer/crossroads.py` returns `{"success": False, "detail": "Quantity must be a positive integer."}` when `quantity` is a boolean, non-integer, or `<= 0`, and `DonateItemRequest.quantity` in `backend/multiplayer/schemas.py` now enforces `gt=0` (default 1) so invalid requests are rejected with HTTP 422 at the schema layer. Previously a negative `quantity` silently persisted a Crossroads item row with a negative `stored` amount, corrupting the shared economy.
- Donating a lore fragment to the Crossroads no longer permanently destroys it: `donate_lore()` in `backend/multiplayer/crossroads.py` previously removed the fragment from `game_state.lore_fragments` entirely, which destroyed the fragment's record and caused collection progress totals to shrink incorrectly. It now sets a `donated` flag on the fragment (kept in `lore_fragments` for stable collection totals) instead of deleting it, and only selects fragments where `discovered and not donated`, so a fragment can no longer be donated twice. `LoreFragment` gained a `donated: bool = False` field with `to_dict`/`from_dict` support (`backend/models/discovery.py`), `claim_lore()` resets `donated` to `False` on the newly claimed fragment, and `GameState.lore_fragments_collected` (`backend/models/game_state.py`) now counts only fragments that are `discovered and not donated`, so donated fragments stay in the collection list but no longer count as 'collected'.
- Faction mission ids were generated with an inconsistent seed, so after completing a mission the ids advertised by `GET /api/game/{id}/missions` no longer matched the ids regenerated by `POST /api/game/{id}/missions/{mission_id}/accept`, causing mission acceptance to fail. Added `get_faction_completed_count()` in `backend/missions.py` and made both `api_missions` and `api_accept_mission` in `backend/api/routes.py` seed `generate_missions()` with the faction completed-mission count (as `get_missions_summary()` already did), so mission ids stay stable across listing and acceptance. Covered by new regression tests in `tests/test_factions.py`.
- `donate_item` (`POST /api/crossroads/donate-item`) now excludes lore-linked discoveries (any discovery with a non-null `lore_fragment_id`) from donation, so donating an item whose name matches a lore-linked discovery no longer silently removes and destroys it. Only discoveries without a `lore_fragment_id` are matched and removed; lore fragments must be exchanged via `POST /api/crossroads/donate-lore`. When no eligible non-lore discovery matches the requested name, the call returns `{"success": False, "detail": "No discovery named '<name>' in cargo."}` as before. Covered by new regression tests in `tests/test_multiplayer.py`.
- Crossroads claim endpoints (`api_claim_item` for `POST /api/crossroads/claim-item/{item_id}` and `api_claim_lore` for `POST /api/crossroads/claim-lore/{donation_id}` in `backend/multiplayer/api.py`) returned the raw claimed item/lore dict, which included the raw `donor_game_id` and `claimer_game_id` fields. They now route the response through the existing `_public_item_view` / `_public_lore_view` sanitizers before returning, so the response's `item` / `lore` object no longer contains raw `donor_game_id` or `claimer_game_id` and instead exposes a stable opaque `donor_id` (12-char SHA-256 digest prefix) — consistent with the already-sanitized public list endpoints (`GET /api/crossroads/items` and `GET /api/crossroads/lore`). Covered by new regression tests in `tests/test_multiplayer.py`.
- `_state_from_dict` (in `backend/game/manager.py`) now returns `None` instead of raising an unhandled exception when the stored save data is corrupt — the input is not a `dict`, a required top-level key (`id`, `seed`, or `ship`) is missing, or `ship` is present but not a `dict` — logging a `logger.warning` for each corrupt-save condition. `load_or_create()` treats a `None` result as "no usable save" and falls back to creating a new game, and the `GET /api/game/{id}` and `POST /api/game/{id}/load` endpoints now return HTTP 404 rather than HTTP 500 for such corrupt saves. Covered by `TestCorruptSaveReturns404` in `tests/test_api.py` and `TestStateFromDictCorruptSave` in `tests/test_generation.py`.
- **Emergency craft now removes the exact targeted discovery**: `emergency_craft` (in `backend/game/engine.py`) now tracks the matching discovery's index via `enumerate` and removes it with `state.discoveries.pop(matching_idx)`, treating a `None` index as "not found". This is a clarity/robustness refactor with no behavior change: the original `state.discoveries.remove(matching_disc)` already removed the exact targeted element, because `Discovery` (a plain `@dataclass` with `id` as its first field and default `eq=True`) generates an `__eq__` that compares every field including `id`, so two discoveries that differ only by `id` are not equal. The refactor simply makes the "remove this specific object" intent explicit and avoids any future dependence on `Discovery.__eq__` continuing to include `id`. The test `test_emergency_craft_removes_discovery_matching_id_and_keeps_others` in `tests/test_game_engine.py` is a characterization test of this observable contract (crafting removes the discovery selected by `id` and leaves value-identical siblings untouched); it is explicitly not a regression test, as the old and new implementations are behaviorally identical and no fixture can distinguish them.
- **Reference browser frontend now stores and sends the per-game auth token**: Previously, under the default-on per-game token enforcement, the reference frontend never sent `X-Game-Token`, so every game-scoped endpoint returned HTTP 403 and the reference client was unusable. Two localStorage-backed helpers, `getGameToken()` and `setGameToken(token)`, were added to `frontend/js/utils.js` using the key `starfarer_game_token` (the same key the webui already uses); `setGameToken(null/falsy)` removes the key. `apiCall()` in `frontend/js/api.js` now reads the token via `getGameToken()` and, when present, attaches it as the `X-Game-Token` header (still setting `Content-Type: application/json`), and `frontend/js/main.js` persists the token returned by `POST /api/game/new` via `setGameToken(data.token)` right after `setGameId(GAME_ID)`. Covered by new tests in `tests/test_frontend_game_token.py`, which verify the helpers exist, `apiCall` attaches the header, `main.js` persists the token, and the backend contract that `/api/game/new` returns a token and game endpoints enforce it (403 without/with the wrong `X-Game-Token`, 200 with the correct one).

### Security
- Ghost signature and discovery-ripple endpoints previously returned raw player data, exposing other players' raw game ids to anyone who could reach them. `GET /api/game/{id}/system/{sys_id}/ghosts`, `POST /api/game/{id}/leave-ghost`, and `GET /api/game/{id}/ripples` now sanitize their responses via new helpers `_public_ghost_view()` and `_public_ripple_view()` in `backend/multiplayer/api.py`. `_public_ghost_view()` strips the ghost's `game_id` and truncates `player_name` to 100 chars and `message` to 500 chars (via the existing `_safe_text` helper); `_public_ripple_view()` strips `source_game_id` and the `acknowledged_by` list (which contained other players' raw game ids) and truncates `source_player_name` to 100 chars and `discovery_name` to 500 chars. `api_system_ghosts`, `api_leave_ghost`, and `api_ripples` now map their results through these helpers before returning, mirroring the existing Crossroads sanitization (`_public_item_view`/`_public_lore_view`/`_public_message_view`) and the leaderboard's opaque `entry_id` fix.
- `GET /api/leaderboard` no longer exposes each game's raw `game_id` or `seed`, which previously let an unauthenticated caller harvest game ids and read any game's full state by default. `get_leaderboard()` in `backend/database.py` now drops both fields and instead exposes a stable, non-reversible opaque `entry_id` — a 12-character SHA-256 hex digest prefix derived from the raw `game_id` via a new `_opaque_entry_id()` helper. A leaderboard entry now contains `entry_id` (opaque), `ship_name`, `last_played`, `discoveries`, `systems_visited`, `credits`, `ghost_signatures_left`, `items_donated`, and `lore_donated` (no `game_id`, no `seed`).
- Per-game access token is no longer persisted inside the shared `state_json` blob written to the `games` and `saves` tables (which broad, non-game-scoped code paths such as `get_leaderboard` and the spectator games-list endpoint parse), eliminating a latent credential exposure. `create_game()` and `save_game()` in `backend/database.py` now strip the `token` key from the state dict before serializing to `state_json` and write it to a dedicated `token` column (`TEXT NOT NULL DEFAULT ''`) on both tables; `load_game()` and `load_save()` read the `token` column and re-inject `data["token"]` so the token round-trips through the column only. A new idempotent `_ensure_token_column()` migration uses `PRAGMA table_info` to add the column only when absent, migrating pre-existing databases. In `backend/game/manager.py`, `game_save()` sets `data["token"] = state.token` and `_state_to_dict()` no longer includes `"token"`. Covered by `TestTokenNotInStateJson` in `tests/test_access_control.py`.
- The long-lived per-game token is no longer accepted via the `token` query parameter on any endpoint — it previously leaked through request logs, proxy caches, browser history, and `Referer` headers because browsers cannot set request headers on `EventSource` connections, so clients were forced to pass the token in the URL for the spectator SSE stream.
- The spectator SSE stream (`GET /api/spectate/{game_id}/stream`) no longer accepts the long-lived token as a query parameter. Instead, a new endpoint `POST /api/spectate/{game_id}/stream-ticket` authenticates via the `X-Game-Token` header and returns `{"ticket": "<opaque string>", "expires_in": 30}` (30-second TTL, single-use); the returned ticket is passed as the `ticket` query parameter of the SSE stream.
