### Fixed
- The spectator SSE stream (`api_spectate_stream` in `backend/api/spectate.py`) now calls `touch_game(game_id)` on every poll iteration, refreshing the watched game to the most-recently-used position in the bounded `GAME_STORE` LRU cache. Previously a game being actively watched over SSE could fall to the least-recently-used position and be evicted mid-stream (dropping the stream's state), since the stream loop read `GAME_STORE.get(game_id)` without refreshing its LRU position. Covered by a regression test (`test_stream_poll_refreshes_lru_position`) in `tests/test_api.py`, which connects to the stream, consumes the initial snapshot, then moves the watched game to the least-recently-used end and drives the poll loop: it asserts the watched game is back at the most-recently-used (last) position in `GAME_STORE`, so the test genuinely fails if the per-iteration `touch_game(game_id)` call is removed (the earlier version of this test was vacuous because `_get_state` already touches the game at connection time, before the first poll).
- `perform_atmospheric_scan` (in `backend/game/engine.py`) previously applied the fuel cost (`ATMOSPHERIC_SCAN_FUEL_COST`) and the body's `atmospheric_scan_count` increment only on the success path (after discoveries were accepted into cargo), so scanning with a full cargo hold could skip both effects and allow free, infinitely repeated atmospheric scans. The fuel cost and `atmospheric_scan_count` increment are now charged up front, before discovery generation and cargo-capacity filtering (mirroring `perform_scan` and `explore_surface`). The `POST /api/game/{id}/atmospheric-scan` route now distinguishes a genuine "not possible" failure from a successful scan whose cargo hold was full: an HTTP 400 now means the scan was genuinely not possible (no current system, no eligible body, insufficient fuel, or the body already at the 3-scan cap), and a full cargo hold returns HTTP 200 with an empty `discoveries` list after still charging 1 fuel and counting the attempt. Covered by a regression test (`test_atmospheric_scan_cargo_full_charges_cost_and_counts_attempt`).
- `perform_sub_surface_exploration` (in `backend/game/engine.py`) now returns a `(ok, discoveries)` tuple (matching `perform_atmospheric_scan`) instead of a bare list, so the `POST /api/game/{id}/sub-surface-explore` route can distinguish a genuine "not possible" failure from a successful exploration whose cargo hold was full. The fuel/crew cost and the body's `sub_surface_explored` flag are charged up front, before discovery generation and cargo-capacity filtering, so a full cargo hold no longer produces a silent charge followed by an HTTP 400 "not possible" response. An HTTP 400 now means the action was genuinely not possible (no current system, insufficient fuel/crew, body not found, unsupported biome, or already explored), never a silent charge. Covered by `test_sub_surface_full_hold_persists_charge`.
- `explore_surface` (in `backend/game/engine.py`) previously applied the surface-exploration fuel cost (`EXPLORE_FUEL_COST`) and the body's `exploration_count` increment only on the success paths (after discoveries were accepted into cargo, and in the `num_finds == 0` early-return branch), so exploring with a full cargo hold could skip both effects and allow free, infinitely repeated surface exploration on the same body. `explore_surface` now charges the fuel cost and increments `exploration_count` up front, before discovery generation and cargo-capacity filtering (mirroring `perform_scan`), while still decrementing `poi_count` only by the number of discoveries actually accepted into cargo (`len(accepted)`) so points of interest are not wasted.
- Mutating game endpoints ignored the `token` query parameter, so clients that could not set request headers (or that consistently passed the token as a query parameter) received HTTP 403 even with a valid token. All state-mutating endpoints in `backend/api/routes.py` (jump, scan, land, atmospheric-scan, sub-surface-explore, explore, event resolve, trade, bulk-sell, upgrade, distress, salvage, salvage/craft, faction mission, missions accept/complete, save, load, hints/dismiss) and in `backend/multiplayer/api.py` (leave-ghost, Crossroads donate/claim item and lore, post-message, acknowledge-ripple) now accept the per-game token via either the `X-Game-Token` header or the `token` query parameter, matching the behavior of read-only endpoints. `_authorize_game` also now rejects a non-string token (`isinstance(token, str)` check) before calling `secrets.compare_digest`.
- Per-game token enforcement (`STARFARER_REQUIRE_GAME_TOKEN`) was previously applied only to state-mutating endpoints, leaving all read endpoints unauthenticated and allowing game-state exfiltration by game ID. - Save load crash on partially-missing/malformed save data: `Discovery.from_dict` and `LoreFragment.from_dict` previously used direct indexing (e.g. `d["id"]`, `d["category"]`) which raised `KeyError` on partial save data. They now use safe `.get()` defaults (`id` → `""`, `category`/`arc` → `"unknown"`, `name`/`title` → `"Unknown"`, `description`/`text` → `""`). `_state_from_dict` now also skips non-dict and malformed discovery/lore-fragment entries (logging a warning for each skipped entry) instead of crashing the entire save load.
- Save history was being destroyed on every save: `create_game()` and `save_game()` in `backend/database.py` used `INSERT OR REPLACE INTO games ...`, which SQLite treats as a DELETE+INSERT on conflict; because the `saves` table has an `ON DELETE CASCADE` foreign key referencing `games(id)`, every save wiped out the entire save history for that game. Replaced with an upsert (`INSERT ... ON CONFLICT(id) DO UPDATE SET ...`) that updates `seed`, `ship_name`, `updated_at`, and `state_json` in place while preserving `created_at` and any child rows. Covered by regression tests in `TestDatabaseSaveHistory` (in `tests/test_data_directory.py`).
- `GameState.apply_choice_outcome` no longer deletes lore-linked discoveries when an event outcome requests a negative cargo delta larger than the number of non-lore cargo items available. Only discoveries without a `lore_fragment_id` are removed; if the requested removal exceeds the number of removable items, the shortfall is ignored and a WARNING is logged ("shortfall ignored"), preserving irreplaceable lore collection progress.
- The in-memory `GAME_STORE` cache was previously unbounded and kept every loaded/created game resident in memory indefinitely (a memory-growth/DoS concern). It is now capped at `MAX_IN_MEMORY_GAMES = 200` games with least-recently-used eviction that persists evicted games to SQLite before removing them.
- Cargo capacity was not enforced when exploration actions and Crossroads item claims appended discoveries, so `len(state.discoveries)` could grow past `state.ship.max_cargo`. A new `_add_discoveries(state, discs)` helper in `backend/game/engine.py` now appends discoveries only up to `free = max(0, state.ship.max_cargo - len(state.discoveries))`, silently dropping any excess, calls `sync_cargo()`, and returns the subset actually stored. `explore_surface()`, `perform_atmospheric_scan()`, and `perform_sub_surface_exploration()` all route discovery additions through `_add_discoveries`, and their log message and return value now report the number of discoveries actually stored (which may be fewer than found when the hold fills). Similarly, `claim_item()` in `backend/multiplayer/crossroads.py` now caps claimed items at `max_cargo` and returns `item_data['stored']` (the number actually stored); when the hold fills it logs "Claimed {stored} of {quantity}x {item_name} from the Crossroads (donated by {donor_name}) — cargo hold full." and sets the `cargo_change` log metadata to the stored count rather than the requested quantity.
- `perform_salvage` spare-parts path in `backend/game/engine.py` bypassed cargo-capacity enforcement by appending directly to `state.discoveries` and calling `sync_cargo()`; it now routes the salvage discovery through `_add_discoveries(state, [disc])` and returns an error ("Cargo hold is full — no room to store salvaged parts.") without logging or awarding value when the cargo hold has no free space.
- Crossroads read endpoints (`GET /api/crossroads/items`, `GET /api/crossroads/lore`, `GET /api/crossroads/messages`) were previously unauthenticated and exposed all players' donations and messages (including raw donor/claimer game IDs) to anyone who knew the URL. They now require a `game_id` and call `_authorize_game()` (token via `X-Game-Token` header or `token` query parameter, enforced when `STARFARER_REQUIRE_GAME_TOKEN` is enabled). Responses are sanitized via new helpers `_public_item_view`, `_public_lore_view`, and `_public_message_view`, which strip the raw `donor_game_id`/`claimer_game_id`/`game_id` fields, truncate free text (`donor_name`/`player_name` to 100 chars, `message`/`text` to 500 chars), and expose a stable non-reversible opaque `donor_id` (12-char SHA-256 digest prefix) instead. Items and lore endpoints also gained pagination (`page`/`per_page`, default 25, max 50).
- `perform_bulk_sell` (backend/game/trading.py) no longer silently clamps to available stock when an entry's requested `quantity` exceeds the number of matching discoveries. Such an over-quantity entry is now rejected entirely (none of its units are sold) with an error reported, while valid sibling entries in the same request still sell (partial failure preserved). Previously the request sold all available matching units of that entry.
- Crossroads `donate_item` (`POST /api/crossroads/donate-item`) now rejects non-positive or non-integer `quantity` values before any cargo mutation: a service-layer guard in `backend/multiplayer/crossroads.py` returns `{"success": False, "detail": "Quantity must be a positive integer."}` when `quantity` is a boolean, non-integer, or `<= 0`, and `DonateItemRequest.quantity` in `backend/multiplayer/schemas.py` now enforces `gt=0` (default 1) so invalid requests are rejected with HTTP 422 at the schema layer. Previously a negative `quantity` silently persisted a Crossroads item row with a negative `stored` amount, corrupting the shared economy.
- Donating a lore fragment to the Crossroads no longer permanently destroys it: `donate_lore()` in `backend/multiplayer/crossroads.py` previously removed the fragment from `game_state.lore_fragments` entirely, which destroyed the fragment's record and caused collection progress totals to shrink incorrectly. It now sets a `donated` flag on the fragment (kept in `lore_fragments` for stable collection totals) instead of deleting it, and only selects fragments where `discovered and not donated`, so a fragment can no longer be donated twice. `LoreFragment` gained a `donated: bool = False` field with `to_dict`/`from_dict` support (`backend/models/discovery.py`), `claim_lore()` resets `donated` to `False` on the newly claimed fragment, and `GameState.lore_fragments_collected` (`backend/models/game_state.py`) now counts only fragments that are `discovered and not donated`, so donated fragments stay in the collection list but no longer count as 'collected'.
- Faction mission ids were generated with an inconsistent seed, so after completing a mission the ids advertised by `GET /api/game/{id}/missions` no longer matched the ids regenerated by `POST /api/game/{id}/missions/{mission_id}/accept`, causing mission acceptance to fail. Added `get_faction_completed_count()` in `backend/missions.py` and made both `api_missions` and `api_accept_mission` in `backend/api/routes.py` seed `generate_missions()` with the faction completed-mission count (as `get_missions_summary()` already did), so mission ids stay stable across listing and acceptance. Covered by new regression tests in `tests/test_factions.py`.
- `donate_item` (`POST /api/crossroads/donate-item`) now excludes lore-linked discoveries (any discovery with a non-null `lore_fragment_id`) from donation, so donating an item whose name matches a lore-linked discovery no longer silently removes and destroys it. Only discoveries without a `lore_fragment_id` are matched and removed; lore fragments must be exchanged via `POST /api/crossroads/donate-lore`. When no eligible non-lore discovery matches the requested name, the call returns `{"success": False, "detail": "No discovery named '<name>' in cargo."}` as before. Covered by new regression tests in `tests/test_multiplayer.py`.
- Crossroads claim endpoints (`api_claim_item` for `POST /api/crossroads/claim-item/{item_id}` and `api_claim_lore` for `POST /api/crossroads/claim-lore/{donation_id}` in `backend/multiplayer/api.py`) returned the raw claimed item/lore dict, which included the raw `donor_game_id` and `claimer_game_id` fields. They now route the response through the existing `_public_item_view` / `_public_lore_view` sanitizers before returning, so the response's `item` / `lore` object no longer contains raw `donor_game_id` or `claimer_game_id` and instead exposes a stable opaque `donor_id` (12-char SHA-256 digest prefix) — consistent with the already-sanitized public list endpoints (`GET /api/crossroads/items` and `GET /api/crossroads/lore`). Covered by new regression tests in `tests/test_multiplayer.py`.
- `_state_from_dict` (in `backend/game/manager.py`) now returns `None` instead of raising an unhandled exception when the stored save data is corrupt — the input is not a `dict`, a required top-level key (`id`, `seed`, or `ship`) is missing, or `ship` is present but not a `dict` — logging a `logger.warning` for each corrupt-save condition. `load_or_create()` treats a `None` result as "no usable save" and falls back to creating a new game, and the `GET /api/game/{id}` and `POST /api/game/{id}/load` endpoints now return HTTP 404 rather than HTTP 500 for such corrupt saves. Covered by `TestCorruptSaveReturns404` in `tests/test_api.py` and `TestStateFromDictCorruptSave` in `tests/test_generation.py`.

### Security
- Ghost signature and discovery-ripple endpoints previously returned raw player data, exposing other players' raw game ids to anyone who could reach them. `GET /api/game/{id}/system/{sys_id}/ghosts`, `POST /api/game/{id}/leave-ghost`, and `GET /api/game/{id}/ripples` now sanitize their responses via new helpers `_public_ghost_view()` and `_public_ripple_view()` in `backend/multiplayer/api.py`. `_public_ghost_view()` strips the ghost's `game_id` and truncates `player_name` to 100 chars and `message` to 500 chars (via the existing `_safe_text` helper); `_public_ripple_view()` strips `source_game_id` and the `acknowledged_by` list (which contained other players' raw game ids) and truncates `source_player_name` to 100 chars and `discovery_name` to 500 chars. `api_system_ghosts`, `api_leave_ghost`, and `api_ripples` now map their results through these helpers before returning, mirroring the existing Crossroads sanitization (`_public_item_view`/`_public_lore_view`/`_public_message_view`) and the leaderboard's opaque `entry_id` fix.
- `GET /api/leaderboard` no longer exposes each game's raw `game_id` or `seed`, which previously let an unauthenticated caller harvest game ids and read any game's full state by default. `get_leaderboard()` in `backend/database.py` now drops both fields and instead exposes a stable, non-reversible opaque `entry_id` — a 12-character SHA-256 hex digest prefix derived from the raw `game_id` via a new `_opaque_entry_id()` helper. A leaderboard entry now contains `entry_id` (opaque), `ship_name`, `last_played`, `discoveries`, `systems_visited`, `credits`, `ghost_signatures_left`, `items_donated`, and `lore_donated` (no `game_id`, no `seed`).
- Per-game access token is no longer persisted inside the shared `state_json` blob written to the `games` and `saves` tables (which broad, non-game-scoped code paths such as `get_leaderboard` and the spectator games-list endpoint parse), eliminating a latent credential exposure. `create_game()` and `save_game()` in `backend/database.py` now strip the `token` key from the state dict before serializing to `state_json` and write it to a dedicated `token` column (`TEXT NOT NULL DEFAULT ''`) on both tables; `load_game()` and `load_save()` read the `token` column and re-inject `data["token"]` so the token round-trips through the column only. A new idempotent `_ensure_token_column()` migration uses `PRAGMA table_info` to add the column only when absent, migrating pre-existing databases. In `backend/game/manager.py`, `game_save()` sets `data["token"] = state.token` and `_state_to_dict()` no longer includes `"token"`. Covered by `TestTokenNotInStateJson` in `tests/test_access_control.py`.
- The long-lived per-game token is no longer accepted via the `token` query parameter on any endpoint — it previously leaked through request logs, proxy caches, browser history, and `Referer` headers because browsers cannot set request headers on `EventSource` connections, so clients were forced to pass the token in the URL for the spectator SSE stream.
- The spectator SSE stream (`GET /api/spectate/{game_id}/stream`) no longer accepts the long-lived token as a query parameter. Instead, a new endpoint `POST /api/spectate/{game_id}/stream-ticket` authenticates via the `X-Game-Token` header and returns `{"ticket": "<opaque string>", "expires_in": 30}` (30-second TTL, single-use); the returned ticket is passed as the `ticket` query parameter of the SSE stream.
